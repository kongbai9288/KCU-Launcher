### 2.2b `FCL/src/main/java/com/tungsten/fclauncher/utils/KcuNativeSync.java` 【新增】

v0.17.0 新建。玩家自带 .so 的双层目录同步。
`/sdcard/KCU/natives/<abi>/`（公共，可读写）→ 校验 ELF → 复制到 `runtime_mod/`（私有，可执行）。
挂载点 `FCLauncher.launchProcess` 内 **`setEnv` 之前**。
零污染：源目录不存在时立即返回，不创建任何东西。

### 2.2c `FCL/src/main/java/com/tungsten/fclauncher/FCLauncher.java`

v0.17.0：`launchProcess` 内在 `setEnv` 前插入 `KcuNativeSync.sync()`。

### 2.2k 【重大】谎报成功事故修复（v0.25.0）

**自 v0.17.0 起编译实际一直失败，APK 从未产出，但每轮都报 success。**

根因：`build.yml` 用 `GE=${PIPESTATUS[0]}` 拿到 gradle 退出码后，只写入 `GRADLE_OK` 环境变量，**没有任何一步以非零状态退出**。step 末条命令是 `echo`，永远成功 → job success。`GRADLE_OK=false` 只喂给 issue 上报，与 job 结论脱钩。

验证实验：注入语法错误 canary → job 仍 success，但 artifacts = 0、产生 5 条"build 失败" issue。

真实编译错误（从告警 issue 正文日志尾部取出）：

```
KcuNativeSync.java:153: error: incompatible types: Set<String> cannot be converted to List<String>
        writeLines(record, kept);
```

修复：

### 2.2x 自带 .so 加载顺序控制（v0.38.0）

用户要求：`.so` 同级放 json 控序，**该文件不能进入加载流程**。

**"不放到加载当中"的两层含义**：① 复制层——json 不能被复制进 `MOD_RUNTIME_DIR`（`KcuNativeSync.sync()` 已按 `.so` 后缀 + ELF magic 双重过滤，天然排除）；② dlopen 层——新增代码只处理 `order` 里声明的、以 `.so` 结尾、且确实存在于运行时目录的文件。

**为什么必须显式 dlopen**：`LD_LIBRARY_PATH` 只影响依赖库搜索路径，**不控制 dlopen 顺序**。顺序敏感场景（符号解析、初始化次序）必须显式按序加载。

**接入点时序关键**：`loadInOrder` 必须在 `setEnv` **之后**——`setEnv` 之前 native 侧还没拿到含 `MOD_RUNTIME_DIR` 的 `LD_LIBRARY_PATH`，此时 dlopen 解析不到依赖库。插入点 `FCLauncher.java:567`，位于 `setEnv` 与 `setUpJavaRuntime` 之间。

契约 `/sdcard/KCU/natives/<abi>/load_order.json`：`abi`（可选，不符则整份不生效）、`order`（文件名数组）、`onFailure`（`abort`/其他）。

**审核要点**：`isSafeName` 拒绝含 `/`、`\`、以 `.` 开头、非 `.so` 结尾的名字（防路径穿越与误加载配置文件）；`abi` 不匹配返回 null；json 损坏等同未配置；`JsonReader` 在 finally 关闭；只加载 `so.isFile()` 为真的（即已过 ELF 校验的）。

**遗留缺口**：`onFailure=abort` 的返回值当前未被调用方使用，**行为等同 skip**。要真正中止需改 `FCLauncher` 异常路径，留待确认语义。

### 2.2y 实例级加载顺序配置（v0.39.0）

用户要求：配置每个实例独立；默认生成的配置要含原有的 .so 以便排序。

路径改为 `<实例目录>/natives/load_order.json`，实例目录取 `config.getWorkingDir()`（同方法内 `bridge.chdir(config.getWorkingDir())` 已在用，来源可靠）。`FCLPath.MOD_RUNTIME_DIR` 里原有库与玩家自带库同在，模板列表即扫该目录。

**关键决策 `enabled` 字段（偏离用户字面要求，可推翻）**：用户未要求该字段。若模板生成后即生效，"什么都不设置"的玩家第一次启动后就会被按序 dlopen 一遍所有库，**默认行为被改变**，违背零污染原则与 v0.38.0 确立的"不放 json 就等同上游"。故模板 `enabled=false` 不生效，用户显式启用才加载；生成时本次也直接 return，避免"刚生成就被用上"。

模板格式：`enabled`(false)、`abi`(当前)、`onFailure`(skip)、`order`(运行时目录全部 .so 按名排序)。

### 2.3e TouchController 尺寸遗留修复（v0.45.0）

承接 v0.44.0 遗留：GameMenu 行 797-801 把 getScreenWidth/Height 传给 TouchController 构造与 TouchControllerInputView.setSize，窗口变化后不更新。当时未修是因为不确定其是否有 resize 接口，本轮读完实现后确认：**它没有 resize 接口但也不需要 —— 尺寸只用于归一化**。

TouchController 中 `addPointer(pointerId, event.getX(index) / width, ...)` 与 `client.moveView(true, deltaY / height, deltaX / width)` 把像素坐标归一化到 0~1，width/height 只作分母，声明为构造参数 val 后即冻结。TouchControllerInputView 的 width/height 由 setSize 写入，用于把 cursorRect 与 inputAreaRect（归一化）换算回像素，共 8 处。

修法：两处都改为动态 getter，构造或传入值仅作兜底（`getScreenWidth().takeIf { it > 0 } ?: initialWidth`）。**不需要任何外部 hook** —— 窗口变化后 DisplayUtil 由 FCLActivity.onConfigurationChanged 刷新，getter 下次调用自动拿到新值。

**真实编译失败一次**：run 40067197166 五架构全失败，报 `TouchControllerInputView.kt:71:28 Accidental override: The following declarations have the same JVM signature (getWidth()I)`。原因是该类继承 View，Android 已有 getWidth 与 getHeight，自定义的 `private val width get()` 编译后同样生成 getWidth 造成 JVM 签名冲突。修法为属性改名 screenW/screenH 并精确替换 8 处使用点（须避开 cursorRect.width 这类 RectF 自身字段，故用完整表达式逐条 assert count 等于一后替换）。TouchController 是普通类不继承 View 故无冲突。日志能拿到靠 v0.40.0 修的"上报步骤直接读 /tmp/build.log"。

### 2.3o 标识体系与实例注册表（v0.55.0）

### 2.3u 指纹去抖动与扫描性能保护（v0.61.0）

审核发现并修正一个会让性能优化失效的缺陷：存档指纹掺入了 lastModified。玩游戏会在世界目录内创建或改动条目，使目录修改时间变化，于是每次启动指纹都不同，跳过扫描这个优化形同虚设。改为只用排序后的世界目录名集合推导指纹，目录名只在世界被新建或被拷入时才变化，这正是需要重新扫描的时机，其余情况稳定。

排序是必需的：listFiles 的返回顺序不保证稳定，不排序会让内容没变被判成变了，同样导致频繁重扫。

已知代价并如实写明：用同名世界目录整体覆盖时目录名不变，指纹不变，不会重新扫描。这是为换取稳定跳过而接受的取舍，不是缺陷隐藏。

给存档扫描加两道性能保护。一是单次扫描世界数上限 32，因为扫描跑在启动路径上，每个世界都要解压并解析一次 level.dat，世界多时会明显拖慢启动；超出上限后本次不再继续，结果可能不完整，属已知取舍。二是 level.dat 体积上限 64MB，正常文件远小于此，异常大的多半已损坏，跳过以免解压拖慢启动。

两道保护都符合已有的宁可漏报也不误报原则：漏报只是没提示，误报会让玩家在没问题的存档上做无谓操作。

编译验证：run 40147991936 全矩阵 success 五个产物。

未验证：指纹改动后的实际跳过率从未在真机测量；32 个上限是否合适未实测。

遗留：来源不明的实例每次启动仍会扫描存档，因为 rememberSaves 只对归属为 kcu 的实例生效，这是刻意保留的保守取舍，代价是迁移来的主力实例每次启动都要解析一遍存档。

有不一致时不标记：玩家还没处理，下次启动仍需提示，不能因为提示过一次就不再提示。

标记时不动实例目录内的标记文件：那表示实例由本启动器创建，而扫描通过只说明这批存档与本账号一致，两者不是一回事，混用会让来源不明的实例被当成自建实例。

### 2.3y 外设策略改为条件行为（v0.65.0）

审查发现并修复一个会让布局永久消失的缺陷。上一轮外设自动关布局时调用了 menuSetting.setKcuLayoutEnabled(false)，而 menuSetting 注册了持久化监听会把值写入 menu_setting.json。后果是玩家插着 OTG 或手柄玩一次后，即使拔掉外设，下次启动读到的仍是 false，布局再也不出现，玩家只会以为启动器坏了。根本原因是把条件行为错误地做成了永久设置。

修法是把玩家意图与外设策略分离。isKcuLayoutEnabled 只表示玩家意图且只有玩家手动切换才写，外设情况每次启动重新判断、不落盘。新增 applyPeripheralPolicy 取代 autoDisableLayoutOnPhysicalInput，每次启动计算 wantEmpty 等于玩家意图为关或检测到外设，与当前状态一致时直接返回不做任何切换。

加状态一致即返回这一判断很重要：每次启动无脑调 applyLayoutEnabled(true) 会把玩家自己在管理页选的布局重置成上次记住的那个，等于玩家的选择白做。只在确实需要切换时才动作。

新增 layoutUserOverride 运行时标记。玩家在插着外设时手动打开布局说明他此刻想要按键，若策略继续生效他刚打开就会被关掉，看起来像开关失灵。该标记只存内存不持久化，否则手动开过一次会让自动策略以后永远失效。

提示逻辑也一并修正：只有因外设而关闭时才弹提示，玩家自己手动关的不必再告诉他。

顺带审查确认两处安全：menuSetting 在 706 至 720 行已初始化且有 new MenuSetting 兜底，735 行调用不会空指针；空布局下 selectDefaultViewGroup 有 viewGroups 非空判断、initializeController 遍历空列表均安全。

编译验证：run 40155991472 全矩阵 success 五个产物。

未验证：拔掉外设后布局是否真能自动恢复从未在真机跑过；外设检测在真实设备上是否会误判未验证；整个布局系统仍未在真机显示过一次。

### 2.3z 预设标记改为按名记录（v0.66.0）

审查发现上一轮的预设补齐标记是盲的。ensurePresetsOnce 用单个存在性标记 .kcu_presets 表示已初始化，一旦标记存在就不再补齐。后果是以后每新增一套预设布局，老用户因为标记已存在就永远拿不到它，等于每加一套布局都要废弃一次老用户的升级路径。

改为 ensurePresets：标记文件不再只表示是否初始化，而是逐行记录已处理过的资产文件名。每次启动读取已处理名单，只对不在名单内的资产执行落盘，处理完把新名字追加回名单。这样以后新增的预设自然会被补齐，而玩家删除过的预设因为名字已在名单里不会被重新加回来，删除依然有效。

标记文件损坏或读取失败时保守跳过而不是清空重来。重来会把玩家删掉的预设加回来，那比少补一套布局更容易引起困惑。

解析出 null 的布局也记为已处理，否则每次启动都会重试同一个坏文件。

实现时回避了 java.nio.file.Files：它要求 API 26，项目 minSdk 恰为 26 处于边界上，没必要为此承担风险，改用 java.io 的 BufferedReader 与 BufferedWriter，语义相同且无版本约束。

编译失败过一次并如实记录：Controllers.java 第 255 行报错 try 没有 catch、finally 或资源声明。原因是我按行号区间替换代码块时把原本的 catch 行一并替换掉了，新版代码只补了内层 try finally 而外层 try 没有收尾。已补回 catch。这类错误编译期就能发现，但如果没有 v0.40 建立的日志取证手段就只能盲猜。

编译验证：run 40157415838 全矩阵 success 五个产物。

未验证：补齐逻辑从未在真机执行，标记文件内容是否正确未验证；新增预设能否真被补齐未验证；布局本身仍一次都没在真机上显示过。

### 2.3aa 不再覆盖玩家显式选择的空布局（v0.67.0）

审查发现上一轮的外设策略会覆盖玩家的明确选择。空布局 KCU Empty 是关闭布局的内部实现，但它作为普通布局出现在可选列表里，玩家可以在设置中主动选中它以使用纯外设不要虚拟按键。上一轮逻辑在启动时计算 wantEmpty 为假而当前是空布局时会调用 applyLayoutEnabled(true)，把玩家主动选的空布局强制换成有按键的布局，玩家每次启动的选择都会被改掉。

修法是区分无按键状态的来源。新增 layoutAutoClosed 内存标记，只有玩家没关布局且纯粹因检测到外设才关闭的情况才算自动关闭并置位。还原分支改成只在 layoutAutoClosed 为真时才执行，玩家自己选的空布局不再被替他换回来。

同时收紧了提示条件：原来只要 peripheral 为真就提示，现在要求 peripheral 为真且玩家未主动关闭。玩家自己关掉布局时本来就知道自己关了，再弹提示是噪音。

顺带审查确认一处设计取舍未变：切换系统语言后两套同名 KCU 布局会共存于列表。本轮未改，因为改名会影响常态显示，而删除另一种语言的布局文件有丢失玩家编辑内容的风险，收益小于代价。已作为已知取舍记录。

编译验证：run 40159810752 全矩阵 success 五个产物。

未验证：该分支在真机上从未执行过；玩家选中空布局后是否真能保持无按键未验证；整个布局系统仍一次都没在真机上显示过。

### 2.3bb 内存泄漏与空指针专项（v0.68.0）

按用户要求做内存泄漏、异常黑洞、空指针专项审查。审查范围包括自建文件全部 catch 块、static 字段、线程与生命周期，以及关键上游文件的空值调用点。

发现并修复最严重的一处内存泄漏。GameMenu 的 fpsThread 与 memoryThread 是匿名内部类，隐式持有 GameMenu，而 GameMenu 持有 Activity 与多个 View。这两个线程只在 toggleFps(false) 与 toggleMemory(false) 时被 interrupt，而宿主 JVMActivity 的 onDestroy 从不调用它们。结果是一旦玩家开着 FPS 或内存显示退出游戏，线程仍在每秒循环，整条 Activity 引用链无法回收；且每次再进入游戏都会调用一次 toggleFps(true) 新建线程，旧线程不停，线程数随进入次数累积。

修法为三处。一是在 toggleFps 与 toggleMemory 开头无条件先停掉上一个线程，防止累积。二是新增 stopFpsThread 与 stopMemoryThread 两个停止方法并新增 public onDestroy 调用它们，三是 JVMActivity.onDestroy 中在 menu 非空且类型为 GAME 时调用 menu.onDestroy。这些改动不改变可见行为，FPS 与内存显示照常工作。

修复 InterruptedException 被吞掉导致中断失效。两处 catch InterruptedException ignored 没有恢复中断标志，而抛出该异常时中断标志已被 JVM 清除，不恢复的话 while 条件里的 isInterrupted 永远返回假，线程停不下来。已改为 catch 后调用 Thread.currentThread().interrupt() 恢复标志。

修复空指针风险。GameMenu 构造中 activity.getIntent().getExtras().getString 链式调用里 getExtras 可能返回 null，一旦为 null 整个菜单构造抛 NPE。改为先判空，取不到时传 null 给 findControllerById，后者会回退到列表第一项，行为与未指定布局一致，正常路径完全不变。

修复一处静默失败。KcuLaunchGate 选完运行时保存设置失败时异常被吞掉且照常启动，玩家会以为自己选过了，下次启动又弹同一个框。改为记录日志并弹出提示，新增字符串 kcu_pick_java_save_failed。

明确未修改的部分。扫描共发现 36 处只含注释的 catch 块，其中绝大多数是文件读写失败后取默认值的正常降级路径，改动它们无收益。ControlButton、ViewManager 等上游文件中大量 getController 与 getMenuSetting 未判空的调用属于上游既有设计，在正常使用流程中不会为 null，逐个加判空会大范围改动上游代码，风险高于收益，因此保留原样并记录。

本轮发生一次严重事故并如实记录。上传 JVMActivity.java 时误用了本地一份 v0.48 包名迁移之前的陈旧副本，package 仍是 com.tungsten.fcl.activity，把迁移后的正确文件整个覆盖，导致 GameService.kt 解析不到 JVMActivity 而五架构全崩。已从 v0.67 的 commit 取回正确版本重新应用改动并恢复编译，其余四个文件经 blob sha 比对确认基线一致未被污染。

编译验证：run 40162355431 全矩阵 success 五个产物。

未验证：线程是否真在退出后停止从未在真机观察；Activity 泄漏是否真消除未用内存分析工具确认；中断恢复与判空分支在真机从未触发过；整个应用仍一次都没在真机安装运行过。

### 2.3cc 自动点击循环泄漏修复（v0.69.0）

延续上一轮的泄漏专项，继续排查消息队列类泄漏。找到 ControlButton 的自动点击循环：autoClickRunnable 只要 autoClick 为真就每 20 毫秒自我重投一次，而关闭自动点击的 handleAutoClick(event, false) 只把标志置假、不移除消息队列里的待执行任务，没有任何外部停止入口。

泄漏链条为：消息队列持有 Runnable，Runnable 是匿名内部类持有 ControlButton，ControlButton 持有 GameMenu，GameMenu 持有 Activity 与多个 View。玩家开着自动点击直接退出游戏时，宿主销毁并不会让这个循环停下，消息队列一直持有整条引用链，Activity 无法回收，且循环仍在每 20 毫秒持续发送按键事件。

修法为新增 ControlButton.cancelPendingEvents，把 autoClick 置假并用 removeCallbacks 同时清掉自动点击与长按两个待执行任务。GameMenu.onDestroy 中遍历 baseLayout 全部子视图，对 ControlButton 逐个调用。ControlButton 是唯一实现了 CustomView 且持有 Handler 的控件，已全仓确认无遗漏。

严格不改变正常逻辑：取消只在宿主销毁路径调用，游戏进行中关闭自动点击仍走原来的 handleAutoClick，两条路径互不干扰。移除的是尚未执行的延时任务，正在发生的按键行为不受影响。

明确不改的一处：ViewManager 加载进度对话框的 postDelayed 已有 loadDialog 等于 dialog 的实例比对保护，属于上游既有的防重入设计，改动收益低于风险，保留原样。

追加防错规则 189 至 195 共 7 条。其中 189 至 191 直接来自上一轮误传陈旧 JVMActivity 的事故：上传前必须逐文件校验 package 行与 com.tungsten 残留数，出 Unresolved reference 时先怀疑文件被旧副本覆盖而非改引用方，批量上传时用 blob sha 确认基线未被污染。192 至 195 是本次线程与消息队列泄漏的通用规律。

编译验证：run 40165304484 全矩阵 success 五个产物。

未验证：自动点击循环中退出游戏后是否真停止从未在真机观察；Activity 是否真被回收未用内存分析工具确认；自动点击功能本身是否正常未验证；整个应用仍一次都没在真机安装运行过。

### 2.3dd 启动前弹窗可取消导致启动无反应（v0.70.0）

继续启动流程审查，找到一个会让玩家以为启动器坏掉的问题。KcuLaunchGate 的存档身份劝导弹窗 showUuidAdvice 没有设置不可取消，玩家可以按返回键或点击对话框外部让它消失，而对话框的继续回调里才调用 proceed.run()。弹窗一消失 proceed 就永不执行，表现为玩家点了启动、弹窗闪一下就没了、游戏始终不启动，且没有任何提示。

这个弹窗是 v0.55 之后补的，而同文件的选运行时弹窗 showJavaPicker 当初就写了 setCancelable(false) 并注明原因是按返回键会让 proceed 永不执行。同一个教训在同一个文件的后加方法里重复出现，说明当时只防了先写的那个。

修法为给劝导弹窗补 setCancelable(false) 与 setCanceledOnTouchOutside(false)。只关返回键不够，点击对话框外部同样会让它消失，两道必须一起关，否则返回键那道防护形同虚设。该弹窗只做劝导不改写存档，唯一出口就是继续启动，与选运行时弹窗的语义一致。

顺带补齐选运行时弹窗：它原本只有 setCancelable(false)，缺少 setCanceledOnTouchOutside(false)，存在同样一条取消路径未堵。一并补上并清理了因此重复的两行注释。

明确不改的一处：统一登录对话框 KcuUnifiedLoginDialog 保持可取消。它不是启动流程，取消的语义是我不加账号了，符合直觉，且它有自己的 dismiss 回调链，不存在 proceed 不执行的问题。

本轮上传严格遵守 v0.69 新增的防错规则 189，上传前逐文件校验了 package 行与 com.tungsten 残留数，本地与远端均为迁移后的正确版本，未再次出现旧副本覆盖。

编译验证：run 40166524106 全矩阵 success 五个产物。

未验证：按返回键与点外部的实际行为从未在真机触发过；劝导弹窗本身从未在真机显示过；整个应用仍一次都没在真机安装运行过。

### 2.3ee 添加账号失败静默（v0.71.0）

继续登录流程审查。KcuUnifiedLoginDialog 的 finishWithOffline 在调用 Accounts.addAccount 与 setSelectedAccount 时用 catch Throwable ignored 吞掉全部异常，随后无条件 dismiss。写入失败时对话框照常消失，玩家以为账号已经建好了，回到账号列表却是空的，且整个过程没有任何提示说明失败原因。这是沉默失败里最容易被当成启动器有 bug 的一类。

修法为在 catch 块中记录日志并弹出 Toast 提示，新增字符串 kcu_login_add_failed。仍然继续 dismiss，不改变流程走向：账号写入失败已经发生，把对话框留在屏幕上没有任何意义，但必须让玩家知道结果，而不是让它悄悄过去。

同一批审查还确认了三处保持原样并说明理由。一是该对话框保持可取消，它不是启动流程，取消的语义是我不加账号了，符合直觉，且 dismiss 回调链完整，不存在回调不执行的问题。二是探测失败后的服务不可用页只提供以填写名称离线进入的按钮，不提供重试，这是既有设计取舍，本轮未动。三是正版分支选择微软登录后 new CreateAccountDialog 的异常被吞掉，这属于上游对话框的构造，改动涉及上游 UI 类，风险高于收益，保留并记录。

本轮上传严格遵守防错规则 189，逐文件校验了 package 行与 com.tungsten 残留数，本地与远端均为迁移后的正确版本。

编译验证：run 40167958985 全矩阵 success 五个产物。

未验证：Toast 从未在真机显示过；添加账号失败的分支从未真实触发过；统一登录流程整体从未在真机跑通过；整个应用仍一次都没在真机安装运行过。

### 2.3ff 迁移导入结果对玩家不可见（v0.72.0）

继续黑洞审查。KcuAccountTransfer.importPending 返回实际导入的账号数量，但唯一调用点 SplashActivity 用 runCatching 包住后完全没有接收返回值，结果被丢弃。这是一个结果黑洞：玩家用外部迁移工具放好待导入文件、启动后正等着账号出现，无论导入成功几个还是一个都没导入成功，界面都不会有任何表示。最坏情况是名称非法、已存在同名账号或写入失败导致一个都没导入，玩家进游戏发现账号全没了，只会认为启动器把自己的账号弄丢了。

修法分三处。一是给 importPending 的返回值区分语义：新增常量 NO_PENDING_FILE 等于负一，表示文件不存在或状态不是待导入，属于正常无操作；大于等于零表示确实处理过一份待导入文件。这样调用方能区分没有迁移文件的常态与有文件却没导入成功的异常。二是单个账号写入失败不再静默，记录日志并继续处理其余账号，不中断整批导入。三是 SplashActivity 接收返回值并弹出提示，导入成功显示数量，处理过却是零个则说明名称无效或已存在。

提示严格只在确实存在待导入文件时出现，没有迁移文件属于常态，不应打扰玩家。提示在主线程弹出，避免在 IO 线程直接调用导致缺少 Looper 的崩溃，并改用 applicationContext 以免 Toast 持有 Activity 引用。新增字符串 kcu_transfer_imported 与 kcu_transfer_none。

本轮上传遵守防错规则 189，逐文件校验了 package 行与 com.tungsten 残留数，本地与远端均为迁移后的正确版本。

### 5.3 版本不一致（v0.16.0 发现并修）

`build.gradle.kts` 曾长期停在 `0.9.0 / 9`，而 `version_map.json` 与 `CHANGELOG` 已到 0.15.0。
**后果**：产物名一直是 `KCU-release-0.9.0-*.apk`，与文档版本号对不上——前面几轮报的产物名全部是 0.9.0。

v0.16.0 同步为 `0.15.0 / 15`，并用产物名证实：

```
./FCL/build/outputs/apk/release/KCU-release-0.15.0-arm64-v8a.apk  172648037 bytes
sha256 e006b5269ed5c94bc08d356dc0342efd7ad9e6bcdaabdcb41d5ef2fe694e3385
```

**教训**：`build.gradle.kts` 是版本号的**唯一真源**（产物名由它决定），`version_map.json` 是手工维护的记录。两者必须每轮同步，否则文档声称的版本与真实产物脱节。

### 5.4 CI 误报（已修，历史噪音已清）

曾因临时开启「始终上报」导致被跳过的矩阵任务（手动指定 arch 时）也被上报为"失败"，产生 issue #28–#37 共 10 条噪音。
真正的抑制条件是 `github.event.inputs.arch == matrix.arch`，已验证有效。**不要为了取证长期开启 always() 上报。**

## 6. 维护纪律

1. **每轮改动必须更新本台账**（§1 加一行，§2 对应文件加一行）
2. **源码改动一律带 `KCU` 标记**，便于全局检索
3. **改完同步三处**：`build.gradle.kts` 版本号 + `version_map.json` + `CHANGELOG.md`
4. **不要运行 `updateMap` 任务**，它会用 build.gradle 的值覆盖 version_map 的历史条目

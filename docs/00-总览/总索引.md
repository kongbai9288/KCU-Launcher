## 3. 关键结论速查（容易忘、且错了会出事的）

### 3.1 不可动的标识

| 标识 | 为什么不能动 |
|---|---|
| `FCL_VERSION_CODE` | **MobileGlues 启动器白名单环境变量名**。改了渲染器判 unsupported，玩家配置全失效 |
| `FoldCraftLauncher` / `FCL-Team` / `Fold Craft Launcher` | 上游署名，GPL 衍生关系 |
| `applicationId = com.kcu.launcher` | 改了用户无法覆盖安装升级 |
| `modpack_files_fclversion_cfg` | 是文件格式名 `.fclversion.cfg`，不是应用名 |

### 3.2 数据契约（外部工具依赖）

| 路径 | 用途 |
|---|---|
| `/sdcard/KCU/manifest.json` | 迁移工具读取 |
| `/sdcard/KCU/dev_mode` | 开发者模式开关，**哈希校验**：`4c238702173b7a01d082f2c6f840d8f149e28e6b081a60e54b452d7c9c5453e0` |
| `<实例>/natives/load_order.json` | 自带 so 加载顺序，含 `enabled` 字段（默认 false） |
| `<版本目录>/kcu_meta.json` | 导入版本元数据：`known` / `display` / `java` |

### 3.3 架构性认知

| 结论 | 说明 |
|---|---|
| **TouchController 已内置且自动启用** | 装了 mod 就生效，零改动 |
| **JNI `FindClass` 是硬约束** | 改 Java 包名不改 C 侧，能编译过、一启动就崩 |
| **Android 资源不依赖文件名** | `fcl_styles.xml` → `kcu_styles.xml` 安全（只引用 `R.style.X`） |
| **`values-night` / `values-v31` 不是语言** | 是夜间模式和 API31+ 资源，绝不能当语言删 |
| **控件尺寸快照是小窗病根** | 七个类构造时存死 `screenWidth`，扩大后指针被 clamp 在旧尺寸内 |

## 4.7 UUID 结论（v0.55.0，用户问过）

**与 HMCL 完全相同** —— 同一份代码：`UUID.nameUUIDFromBytes(("OfflinePlayer:" + name).getBytes(UTF_8))`。

**与 RFC 标准 v3 不同** —— Java 的 `nameUUIDFromBytes` 是 MD5、版本位=3，但**不带命名空间前缀**。

| 算法 | Steve 的结果 |
|---|---|
| MC 离线（本项目 / HMCL） | `5627dd98-e6be-3c21-b8a8-e92344183641` |
| `uuid3(NAMESPACE_DNS, "Steve")` | `e9df5bd1-28bb-31c6-...` |

**结论**：与上游保持一致优先于与通用工具一致 —— 不一致会让玩家失去原有存档归属。

**opennbt 已在项目内**（1.5，世界管理在用），无需移植。

## 9.4 两个真缺陷（v0.64.0）

### ⓿ 预设布局对老用户**完全不生效**

只在"列表为空=全新安装"时落盘 →
**任何已用过的设备永远看不到 KCU 布局**。

→ `ensurePresetsOnce()`：init 扫描后补齐，
标记文件 `.kcu_presets` 保证**只做一次**
（否则玩家删掉会自己长回来）。

### ❶ 滑动链开在指针键上会**中断攻击**

`handleSwipeMove` 在手指**滑出且未命中联动键**时释放当前键。
指针键就是用来**长按拖视角**的，滑出边缘是常态 → 攻击中断。

→ 指针跟随键（`攻击`/`Use`）**不开启**滑动链，其余保持。

## 9.5 外设策略：条件行为而非永久设置（v0.65.0）

上一轮外设自动关时**写了持久化字段**：

```java
menuSetting.setKcuLayoutEnabled(false);  // ← 落盘
```

**后果**：插着 OTG 玩一次 → 拔掉 →
下次启动读到的仍是 false → **布局永久消失**。

### 修法：意图与策略分离

| | 持久化 | 谁改 |
|---|---|---|
| `isKcuLayoutEnabled` | ✅ | **只有玩家手动** |
| 外设情况 | ❌ | 每次启动重新判断 |

两点补充：
- **状态一致即返回** —— 否则每次启动重置玩家选择
- **手动后本次不覆盖**（`layoutUserOverride`，仅内存）

## 9.6 预设标记：从盲标记改为按名记录（v0.66.0）

v0.64 的 `.kcu_presets` 只是个**存在性标记**：

```
标记存在 → 不再补齐
```

**后果**：以后每新增一套预设，老用户**永远拿不到**
→ 每加一套就废弃一次老用户的升级路径。

## 改法

标记文件**逐行记录已处理过的资产文件名**：

| 情况 | 行为 |
|---|---|
| 名字不在名单 | 落盘 + 追加进名单 |
| 名字已在名单 | 跳过（**删除依然有效**） |
| 标记读不出来 | **保守跳过**，不清空重来 |

**不清空重来的理由**：重来会把玩家删掉的预设加回来，
比少补一套更容易让人困惑。

## 9.7 不再覆盖玩家的空布局选择（v0.67.0）

`KCU Empty` 是"关闭布局"的实现，**但它在可选列表里**。

玩家可以在设置里**主动选它**（= 用纯外设、不要虚拟按键）。

v0.65 的逻辑会在启动时把它**强制换回**有按键的布局
→ **玩家每次启动的选择都被改掉。**

### 修法：区分"为什么是无按键"

```java
layoutAutoClosed = peripheral && !userOff;
// 只有自动关掉的才还原；玩家自己选的不动
```

提示也收紧：玩家自己关的**不再弹提示**（噪音）。

### 已知取舍（本轮未改）

切换系统语言后**两套同名 KCU 布局共存**。
改名影响常态显示，删文件有丢失玩家编辑的风险 → **收益小于代价**。

## 9.8 泄漏 / 黑洞 / 空指针专项（v0.68.0）

### ⓿ 真内存泄漏：采样线程

`fpsThread` / `memoryThread` 是**匿名内部类** → 持有 GameMenu →
持有 Activity + 多个 View。

只在 `toggleFps(false)` 时停；**宿主 `onDestroy` 从不调**。

```
开着 FPS 退出游戏 → 线程继续每秒循环 → Activity 无法回收
每进一次游戏 → 新建线程，旧的还在 → 线程累积
```

**修法**（不改变可见行为）：
- 开启前**先停掉**上一个
- 新增 `onDestroy()` + `stopXxxThread()`
- `JVMActivity.onDestroy` 调用

### ❶ 中断标志丢失

```java
catch (InterruptedException ignored) {}   // 标志已被清除
```

→ `while (!isInterrupted())` **永远为真** → 停不下来。

改为 `Thread.currentThread().interrupt();`

### ❷ 空指针

`getIntent().getExtras().getString(...)` —— `getExtras()` 可为 null
→ 整个菜单构造 NPE。已判空，行为不变。

### ❸ 静默失败（改可见）

选 JDK 后**保存失败被吞** → 玩家以为选过了 → 下次又弹。
改为记日志 + 提示。

### 明确**不改**的

| 类别 | 数量 | 理由 |
|---|---|---|
| 只含注释的 catch | 36 处 | 多数是**正常降级**（读写失败取默认值） |
| 上游 `getController()` 未判空 | 多处 | 正常流程不会为 null；大改风险 > 收益 |

### ⚠ 本轮严重事故

**误传了迁移前的旧 `JVMActivity.java`**
（package 仍是 `com.tungsten.fcl`）→ 五架构全崩。
已从 v0.67 commit 取回正确版本。其余 4 文件 sha 比对**未被污染**。

## 9.9 自动点击循环的泄漏（v0.69.0）

```java
autoClickRunnable = new Runnable() {
    public void run() {
        ...
        if (autoClick) autoClickHandler.postDelayed(autoClickRunnable, 20);
    }
};
```

**每 20ms 自我重投**，而关闭只置 `autoClick=false`
—— **不移除队列里的待执行任务，无外部停止入口。**

### 泄漏链

```
消息队列 → Runnable → ControlButton → GameMenu → Activity + View
```

开着自动点击退出游戏 → **循环不停** → Activity 无法回收。

### 修法（不改正常逻辑）

- 新增 `ControlButton.cancelPendingEvents()`
- `GameMenu.onDestroy` 遍历 baseLayout 逐个调用
- **游戏进行中**仍走原 `handleAutoClick` —— 两条路径互不干扰

**全仓确认**：`ControlButton` 是唯一持有 Handler 的 CustomView。


## 9.26 镜像下载优化（v0.83.0）

上一轮以"**还没逐行读完**"列为暂缓 ——

### 解决什么

| 问题 | 表现 |
|---|---|
| 分到慢节点 | **下载长时间卡住不动** |
| 切换后落损坏文件 | **缺显式校验值时不检查** |

### 三道限制 ← 敢做的关键

| # | 限制 |
|---|---|
| 1 | **只在响应带哈希时启用**（非镜像链路全程不生效） |
| 2 | **最多切 2 次**，且**不在最后次重试**启用 |
| 3 | 10s 窗口 **< 128KB/s** 且**剩余超一个窗口** |

- 只在**没有显式校验值**时用镜像哈希兜底
- 哈希**先按 40 位十六进制校验**再用
- **冲突抛错**走常规重试，不采用可疑值
- 下载前**先查哈希缓存**，命中就跳过下载

`getContentLength` → `getContentLengthLong`
**对所有下载生效**，但**只影响进度精度**，
**不改变任何流程分支**。

- 抽象方法签名变更 → **实现类只有 2 个**，无遗漏
- 上游 2 份单元测试**未同步**（不影响产物）

## 9.27 ⚠ 审查发现：镜像下载会全部失败（v0.83.1）

## 9.28 导入页与版本清单审查（v0.84.0）

本轮**没有同步上游** —— 回头查自己写的代码。

### ⓿ 导入失败会留下半截文件（最严重）

原来**直接写最终路径** → 中途失败留下不完整文件。

而**清单路径是先落 json 再下 jar**：

```
半截 jar + 完整 json
→ 版本**照样出现在列表里**
→ 玩家点开是坏的
→ 可界面刚才明明说了"导入失败"
→ 自相矛盾，只会认为启动器有问题
```

改为**先写临时文件，完整才改名**，失败删临时。
**目标路径要么没有文件，要么是完整内容。**

版本 json 写入同样改原子 ——
否则半截 json → 解析不出 → **版本静默缺席**。

### ❶ 版本 id 取错了

原来取**地址路径最后一段**。
但文件选择器返回的 content 地址，
末段常是 `msf:12345` 这种**与文件名无关的串**
→ id 变成毫无意义的名字，**玩家认不出这是哪个版本**。

改为按**显示名**取（复用上轮刚加固的取文件名方法）。

### ❷ 读循环按 `> 0` 判结束

个别流会**返回 0** → 提前结束 → **内容被静默截断**。
三处统一改 `!= -1`。

风险低但成本也低 —— **顺手消除隐患**。

### 两条"本来以为有问题、查证后没问题"

| 怀疑 | 查证结果 |
|---|---|
| 清单顺序注释写反了 | **实际取回核对**：首条 26.3 快照、末条 2009 版 → **注释是对的** |
| 缓存命中拷贝不建目录 | `copyFile` **自己会创建父目录** → **没问题** |

**没凭印象下结论，去查了。**

## 9.29 导入顺序与元数据原子写（v0.85.0）

两处都属于同一类：**失败后留下「看起来能用、实际是坏的」中间状态**。

### ⓿ 先落 json 再落 jar —— 顺序反了

原写法 `download(json) && download(jar)`，两个后果：

| 情形 | 后果 |
|---|---|
| **jar 失败** | json 已完整 → **版本照样进列表，点开是坏的**<br>可界面刚说过"导入失败" → **自相矛盾** |
| **json 失败** | 整次作废，**能下到的 jar 也不下了** → 白等 |

改为**先 jar 后 json**：
- jar 失败 → 清空目录 + 提示（此时**还没有 json**，不留坏版本）
- json 取不到 → **退回写最小 json**，版本依然可用

### ❶ 元数据写入非原子 → 运行时选择被静默重置

`new FileWriter(file, false)` **先截断**。
写一半出问题 → 半截文件 → 读成空值。

**这个文件记录的正是玩家已选过的运行时。**

表现：**明明选过运行时，下次启动又弹一次，且无任何提示**
→ 玩家只会觉得「设置自己丢了」。

改为**先写临时文件、完整才改名**。

### 一条确认后不改的

jar 成功但 json 完全写不出 → 留下只有 jar 的目录。
**缺 json → 不会进列表**，但占磁盘。
删掉会**误伤重复导入已有版本** → 保留，已登记。

### 一类写法权衡后保留

读循环 `> 0` 判结束 —— 上一轮统一过。
本文件还有 2 处同类，但**带长度上限且以 0 为停止**：
- 最坏 = 探测不到真实版本、回退"未知"
- **不会写入截断内容**

改 `!= -1` 有**理论空转风险** → **权衡后保留**。

## 9.30 账号迁移与自定义标识（v0.86.0）

### ⓿ 迁移文件按**部分结果**导入 → **账号永久丢失**（最严重）

```
外部工具写 pending（5 个账号）
→ 第 3 个处损坏
→ readEntries 返回**前 2 个**
→ 导入这 2 个
→ export() 把文件重写成快照
→ 源文件被覆盖 → **第 3、4、5 个找不回来**
```

**这类问题我在实例注册表（v0.81）修过一次 —— 这是第二次。**
这次后果更重：**那次是重新扫描存档，这次是账号丢了**。

修法：解析失败返回 null → **一个都不导入 + 不改写状态**
→ 保留现场，外部工具重新导出即可完整导入。
**少导入可以重来，丢了就没有了。**

**取舍（明说）**：解析失败时**不给提示**。
文件由外部工具生成，玩家自己修不了，提示也无能为力；
保留原样 → 重新导出一次即自动生效。异常记日志。

### ❶ 公共目录文件非原子写

`FileWriter(file, false)` **先截断** → 半截 JSON。

**外部迁移工具也会读这个文件** → 读到坏文件后
**无从判断是启动器写坏还是自己格式不对**。

改临时文件 + 改名。顺带补 `mkdirs()` 返回值检查。

### ❷ 自定义标识用 `apply()` 异步落盘

`apply()` 只保证**进内存**，落盘在之后某刻。

而这个值**决定账号身份、也决定存档比对用哪个标识**。

→ 未落盘就进程终止 → **填过的标识不见了，无提示**
→ 与「选过运行时又弹一次」**同一类**。

改 `commit()` 同步写回（几个字节，开销可忽略），失败也记日志。

## 9.31 一键粘贴到聊天栏 + 输入法空格（v0.87.0）

### ① 一键粘贴（已实现）

**查证结论：上游已有完整通道**

`GameTextSender.send()`：
- 光标模式 → 直接提交到已打开文本框
- 否则 → **先发 T 开聊天栏** → 等通道就绪 → 提交 + 回车

而按钮事件里本来就有 **「发送文本」** = 你说的"提前写好内容"
→ **这条路本来就通**。

**缺的只有"读剪贴板"这一路** → 新增开关 `pasteClipboard`：
- 默认**关闭**（已有布局无此字段 → 按默认，**行为不变**）
- 打开 → 按下即提交那一刻的剪贴板纯文本
- **剪贴板优先于预设文本**
- **剪贴板为空 → 给提示**，不静默跳过

### ② 输入法粘贴前面多空格（根因找到了）

**`TEXT_FILLER = "                              "` —— 30 个空格**

输入框垫着这 30 个空格（为了迁就部分输入法）。

| 场景 | 行为 | 结果 |
|---|---|---|
| 逐字输入 | 新字符**追加在 filler 之后** | ✓ 正常 |
| **复制/粘贴** | 输入法**一次性替换整段** | ✗ **filler 被一起发出** |

**这就是你找不到原因的原因**：
代码里是"占位空格"，界面上是"多一个空格"，**两者对不上**。

**修法**：
- 先**剥掉前导空格**得到有效文本
- 与**上次已提交的有效文本**比对 → 只补发多的、只回退少的
- filler **不参与比对** → 不会被发出
- 输入框清空时**比对基准归零**（否则下次会误删已有内容）

**顺带修正**：回退次数原按整段算 → 改按有效文本算
→ 粘贴到已有内容的聊天框**不再误删前面已输入的部分**。

**已知代价（明说）**：
玩家**真的在开头敲空格** → 那个空格不提交。
聊天开头空格无实际作用，代价**远小于**继续多空格。

**⚠ 无法在编译环境复现不同输入法的粘贴行为**
→ 修的是"按现有代码能解释得通的那条路径"，
**真机是否彻底消除，需要你实际粘贴一次确认**。

## 〇之二、v3 修正（严格审查发现）

v2 用 `config.getRenderer().getGlName().equals("libng_gl4es.so")` 判重。
**缺陷**：插件渲染器的库与内置库是不同文件（`/plugin/libng_gl4es.so` vs
`/native/lib/libng_gl4es.so`），名字相同、路径不同。插件库损坏而内置库完好时，
按库名判重会**误跳过一次有效救援**。

改为按**完整路径**判重（调用处传入失败库的完整路径），并去掉对 `getRenderer()` 的依赖，
少一处可能的异常点。等价验证新增"插件目录同名库损坏"场景，确认现在能正确救援。

## 〇、v2 修正（严格审查发现，已重做）

v1 通过 `RendererManager.INSTANCE.getRendererList()` 取兜底库名。**审查发现该访问有严重副作用**：

`rendererList` 的 getter 带 `if (!isInit) init(context)`，而 `init()` 内部会执行
`RendererPlugin.init(context)` 与 `DriverPlugin.init(context)` —— 在 `:jvm` 进程的启动路径上
触发整个插件系统扫描（文件 IO、插件解析），既拖慢启动，又可能抛出与本次渲染无关的新异常。

**v2 改为直接使用字面量常量。** 内置渲染器库名本就在 `RendererManager.init` 中硬编码，
取字面量与取列表首位完全等价，且零副作用、零初始化、行为确定。

已复核：文件中仅注释提及 RendererManager，代码无任何引用、无 import。

## 一、渲染库加载失败兜底（已落盘，未编译）

### 问题

`KCULauncher.setupGraphicAndSoundEngine` 里两处 `bridge.dlopen()` **返回值从未检查**：

```java
long handle = bridge.dlopen(config.getRenderer().getGLPath());   // 插件分支
...
bridge.dlopen(nativeDir + "/" + config.getRenderer().getGlName());  // 内置分支，连变量都没接
```

`dlopen` 失败返回 0，流程照常继续，游戏随后的 GL 调用会崩 ——
表现为**进游戏黑屏或闪退，用户看不到任何原因**。

失败原因可能有：文件缺失、架构不匹配、依赖库缺失、设备 GLES 能力不足导致初始化失败。

### 改动

加载失败时改用**内置兜底渲染库**再试一次：

- 兜底目标取内置渲染器（`path` 为空，列表首位即 Krypton Wrapper / `libng_gl4es.so`）
- `:jvm` 进程内 `RendererManager` 可能未初始化：访问 `rendererList` 会触发 init；
  仍失败则回落到字面量常量
- 当前渲染器本身已是兜底库时不重复尝试
- **全程 try/catch**：兜底逻辑本身绝不允许抛出新异常
- 兜底失败维持原状（不比改动前更糟），但日志留下明确原因

保持原有分支结构：内置分支仍然**不设置** `RENDERER_HANDLE`。

### 等价验证（8 场景，全部符合预期）

| 场景 | 改前 | 改后 | 结论 |
|---|---|---|---|
| 插件渲染器加载成功 | 1234 | 1234 | 成功路径零额外动作 |
| 插件渲染器失败 + 兜底成功 | 0 | 1234 | 发起兜底并取到句柄 |
| 插件渲染器失败 + 兜底也失败 | 0 | 0 | 维持原状 |
| 内置渲染器加载成功 | 1234 | 1234 | 成功路径零额外动作 |
| 内置渲染器失败 + 兜底成功 | 0 | 0 | 发起兜底加载（原代码不接收句柄） |
| 内置渲染器失败 + 兜底也失败 | 0 | 0 | 维持原状 |
| 当前即兜底库且失败 | 0 | 0 | 不重复尝试 |
| 兜底 dlopen 自身抛异常 | 0 | 0 | 异常被吞，启动不中断 |

语法解析通过（javalang）。等价验证 8 场景全部符合预期（见 `verify_fallback.py`）。

### 必须说清的有效性边界

**内置分支的兜底能否真正生效，不确定。**

原代码在内置分支既不接收 `dlopen` 返回值、也不设 `RENDERER_HANDLE`
（且 `RENDERER_HANDLE` 只在 `SDK_INT < 30` 才设置，现代设备基本不设）。
这说明渲染库的实际生效路径很可能是 **LWJGL 后续按名字自行加载**，
而不是靠启动器预加载的句柄。若如此，预加载兜底库只是"把库load进进程"，
游戏仍会去加载那个失败的名字。

**因此：插件分支的兜底较有把握；内置分支的兜底属于尽力而为，可能无效但无害。**
这一点无法在沙盒验证，需真机观察。

## 二、底层帧率优化 —— 调研结论与诚实评估

### 现有底子（已核实）

项目已有 6 个内置渲染器 + MobileGlues 等插件：

| 渲染器 | 库 | 上限版本 |
|---|---|---|
| Krypton Wrapper（默认） | libng_gl4es.so | 26.3-snapshot-3 |
| Holy-GL4ES | libgl4es_114.so | 1.21.4 |
| VirGLRenderer | libOSMesa_81.so | 26.3-snapshot-3 |
| VGPU | libvgpu.so | 1.16.5 |
| Zink | libglxshim.so | 26.3-snapshot-3 |
| Freedreno | libOSMesa_8.so | 26.3-snapshot-3 |

另有 `VulkanCheckManager`（Vulkan 能力检测）、`isAdrenoGPU()`（GPU 探测）。

**即业界主流 GL 翻译层方案基本已在列。**

### 对四个方向的评估

| 方向 | 判断 | 理由 |
|---|---|---|
| **替换/自研 GL 翻译层** | **不建议** | 主流方案已齐备；自研或改 C 层需重新编译 .so，风险极高，且我无法验证效果 |
| **big.LITTLE 绑核调度** | **不建议，可能适得其反** | 绑核 → 功耗↑ → 温度↑ → 降频 → 帧率反而降。安卓本身已会把前台进程放性能核。绑错核会直接变慢 |
| **ADPF 温度/性能提示**（Apache 2.0，与 GPLv3 兼容） | **价值有限** | 只能监控温度并提示；自动降负载需游戏配合，做不到 |
| **JVM GC/JIT 参数** | **不建议** | Java 8/11/17/21 参数差异大，加错会导致 JVM 启动直接失败。Java 9+ 默认 G1 已是最优默认，额外调参收益小风险大 |
| **madvise 页回收 / SIMD 矩阵内核** | **不适用** | 前者管不到 GPU 显存（真瓶颈在翻译层与 GPU）；后者要改渲染库 C 源码，同上 |

### 结论

**真正最大的帧率杠杆是"选对渲染器"** —— 选错与选对可能差数倍。
项目已有 Vulkan 能力检测与 GPU 探测的支撑，做"按设备能力推荐渲染器"
比任何微优化都更实在，且风险低（只给建议，不擅自改用户已选的）。

除此之外，我没有把握在不做真机验证的前提下交付一个"帧率更高"的底层改动。
宁可说做不到，也不虚构一个效果。

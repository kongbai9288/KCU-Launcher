| 你要求的 | 实际实现 |

## 三、Sodium 检测原理 与 "让检测对象可自定义"（**未实现**）

### 检测原理（已确认，有源码依据）

来源：CaffeineMC/sodium-fabric commit `6eeefda`（Driver probe 系统）
与 NVIDIA 驱动版本检测的实现。

**Sodium 读取三个 GL 字符串来识别环境：**

```java
String vendor   = GL11C.glGetString(GL11C.GL_VENDOR);
String renderer = GL11C.glGetString(GL11C.GL_RENDERER);
String version  = GL11C.glGetString(GL11C.GL_VERSION);
```

判定方式（摘取关键分支）：

- NVIDIA：`vendor.contains("NVIDIA")`，且**仅在 Windows** 启用 workaround（issue1486）
- 旧版实现还走 `GraphicsAdapterProbe` + Windows 驱动存储版本解析

**也就是说：检测对象 = 这三个 GL 字符串。**
你说的"让检测的对象都可以被用户自定义"，落点就在这里。

### 这三个值现在能不能改

| 项 | 现状 | 能否自定义 |
|---|---|---|
| **GL_VERSION** | gl4es `LIBGL_VERSION` **接受字符串**<br>Mesa `MESA_GL_VERSION_OVERRIDE` | ✅ **已有现成机制** |
| **GL_VENDOR** | gl4es 硬编码 `ptitSeb` | ❌ **无环境变量** |
| **GL_RENDERER** | gl4es 硬编码 `GL4ES wrapper` | ❌ **无环境变量** |

**关键事实（重要）：gl4es 不披露真实 GPU。**

gl4es 仓库 issue #502（2026-02 仍在讨论）专门要求它披露底层硬件，
说明**目前不披露**。实际输出：

```
GL_VENDOR:   ptitSeb
GL_RENDERER: GL4ES wrapper
GL_VERSION:  2.1 gl4es wrapper 1.1.7
```

对比 VirGL / Mesa 系**会披露真实 GPU**：

```
GL_VENDOR:   Mesa/X.Org
GL_RENDERER: virgl (Adreno (TM) 740)
```

### 由此得出的判断（请重点看这段）

**在 gl4es 下，Sodium 的驱动黑名单本来就不会触发** ——
因为它看到的是 `ptitSeb`，不是 `NVIDIA` / `Intel`。

所以：

| 情形 | 是否需要自定义检测对象 |
|---|---|
| 用 gl4es 跑 | **本来就不会被 GPU 黑名单命中** |
| 用 VirGL / Zink / MobileGlues（披露真实 GPU） | 才可能被真实 GPU 字符串触发 |

**技术上能不能做到？** 能，但代价不小：

- 需要改 gl4es C 源码，加读环境变量来覆盖 VENDOR/RENDERER
- 我们仓库里的 gl4es 是**预编译 .so**（`libgl4es_114.so` / `libng_gl4es.so`），
  改了就得**自己编译并替换**，还要纳入 CI
- Mesa 侧（virgl/zink）改起来更复杂

属**中等偏高难度**。

### 需要你回答（决定我做不做）

按你说的"量力而行，不能实现就不实现"，我倾向**先别做**，除非你确认场景：

1. **你想绕过的是哪一类检测？**
   - GPU 驱动黑名单（Sodium 的 NVIDIA / Intel）—— gl4es 下本就不触发
   - 某些模组对"低端 / 未知 GPU"的**降级或拒绝**逻辑
   - 别的（请说明）
2. **你实际用哪个渲染器遇到钠的问题？**
   这决定改动落在 gl4es 还是 Mesa 系
3. 如果只是想改 **GL_VERSION**，
   那**成本极低**（现成环境变量），值得做

### 附带：issue2561 不是 GL 字符串

Sodium 的 `-Dsodium.checks.issue2561=false` 是针对
**LWJGL 库版本不兼容**的检测，**不读 GL 字符串**。
我们用的是 LWJGL 3.3.3 / 3.4.1。这条与上表的自定义方案**不是一回事**。

# 上滑多动作方案

> 结论先行：**上游 ControlButton 已经实现了滑动链（swipe chain），不需要引入第三方库，也不需要改一行 Java。**
> 差异化通过「布局 JSON + 事件配置」达成，把上游控件当 API 用。
> 依据：本仓库已落地的 FCL 源码实测（`FCL/src/main/java/com/tungsten/fcl/control/view/`）。

---

## 1. 上游已有什么（实测）

### 1.1 四个独立事件槽

`control/data/ButtonEventData.java`：

| 事件槽 | 触发条件 |
|---|---|
| `pressEvent` | 按下保持（按住期间持续） |
| `longPressEvent` | 长按，阈值 **400ms**（`handler.postDelayed(runnable, 400)`） |
| `clickEvent` | 单击（抬起时 `downTime ≤ 100ms` 且位移 ≤ 10px） |
| `doubleClickEvent` | 双击 |

四个槽彼此独立，各自可配不同键码/动作。**单个按钮原生就支持 4 种操作。**

### 1.2 滑动链（关键）

`ControlButton.onTouchEvent` 内，`ACTION_MOVE` 时若 `getData().getEvent().isSwipable()` 为真则调 `handleSwipeMove(event)`。

`handleSwipeMove` 逻辑（源码注释原文）：

> 滑动链移动：手指在当前按住的按钮内不动，滑出后释放它并按下命中的下一个联动按钮（可滑回自己），悬空滑入任意联动按钮也会按下。

判定与切换：

```java
float parentX = getX() + event.getX();   // 父容器坐标
float parentY = getY() + event.getY();
// 仍在当前按钮矩形内 → 什么都不做
// 滑出 → swipePressed.handleSwipeExit() 释放当前
//      → findSwipableButtonAt(parentX, parentY, null) 找新目标
//      → 命中则 handleSwipeEnter() 按下新目标
```

`ViewManager.findSwipableButtonAt(x, y, exclude)` 的准入条件（全部满足才命中）：

1. 是 `ControlButton`
2. 不是自己（`exclude`）
3. `getVisibility() == View.VISIBLE`
4. `getData().getEvent().isSwipable() == true`
5. 坐标落在其矩形内

遍历顺序：`getChildCount() - 1 → 0`，**从上层往下层找**。

### 1.3 状态字段

`swipeEngaged`：滑动链已触发标志。为真时 `ACTION_UP` 走独立分支——释放链上按钮、**不触发单击/双击**。这意味着滑动手势与点击手势语义完全分离，不会误触。

## 2. 方案：用布局实现上滑，不改代码

### 2.1 原理

`findSwipableButtonAt` 是**纯坐标命中**，与"方向"无关。所以只要把联动按钮放在主按钮的**上方**，手指上滑离开主按钮矩形后进入联动按钮矩形，就会自动完成「释放主按钮 → 按下联动按钮」。

**这就是"上滑执行第二个操作"，零代码改动。**

### 2.2 布局约定（KCU 自定义）

```
        [上 · 动作B]        ← 上滑命中
[左·D]  [ 主按钮 · 动作A ]  [右·C]     ← 上/下/左/右 四个联动按钮环绕
        [下 · 动作E]
```

要求（写入默认布局 JSON）：

| 项 | 值 | 原因 |
|---|---|---|
| 联动按钮 `swipable` | `true` | 否则 `findSwipableButtonAt` 直接跳过 |
| 主按钮 `swipable` | `true` | 滑回自己需要（`swipePressed` 复位） |
| 联动按钮 `visibility` | `VISIBLE` | 硬性准入条件，`GONE`/`INVISIBLE` 不命中 |
| 位置 | 紧贴主按钮边缘，**允许部分重叠** | 缩短滑动距离，手感更接近输入法上滑 |
| 尺寸 | 可小于主按钮 | 够命中即可，不占视觉面积 |
| 视觉 | 透明背景或低透明度 | 用户看不到，但滑得到 |

### 2.3 为什么不用第三方库

用户设想是"用别人的代码"。实测后发现：

- 上游 FCL 自己就是 GPL-3.0 的"别人的代码"，且是官方维护的
- 它已经提供了坐标命中 + 进入/退出回调 + 与点击语义分离的完整实现
- 引入第三方手势库反而要：**新增依赖、处理与 `onTouchEvent` 的事件竞争、绕过已有的 `handleMoveEvent` 指针跟随逻辑**

风险对比：

| 方案 | 改动量 | 风险 |
|---|---|---|
| 布局 + 配置（采用） | 0 行 Java | 无。上游机制原样运行 |
| 第三方手势库 | 需接管 `onTouchEvent` | 与 `pointerFollow`、`acquireLookOwner` 视角独占逻辑冲突，容易滑动时视角乱飘 |
| 自己写方向判定 | 需改 `ControlButton` | 违反"不改上游代码"约束 |

**结论：不引第三方库，用上游已有机制。**

### 2.4 未被覆盖的部分（如实说明）

上游是**坐标命中**，不是**方向映射**。差异：

- 上滑到"上方按钮"→ 命中，OK
- 但如果手指**滑出所有按钮区域后悬空**，`findSwipableButtonAt` 返回 null，`swipePressed` 置空 → 不触发任何动作

即：**必须真的滑到联动按钮上**。这与输入法"上滑一定出表情"略有差别——输入法是在原控件内判定方向，不依赖第二控件存在。

若要做到"在原按钮内上滑即切换"（不依赖第二控件），必须改 `ControlButton.onTouchEvent`，违反约束。**当前不做，登记为待议项。**

缓解：把联动按钮做得足够大且紧贴，实际滑动 20–40px 即可命中，手感接近。

## 3. 布局差异化原则

用户要求：布局与别人不一致，但不改代码，把上游当 API 用。

落地方式：

| 层 | 做法 | 是否改上游代码 |
|---|---|---|
| 控件实现 | 原样复用 `ControlButton` / `ControlDirection` / `TouchPad` | 否 |
| 布局 | 自写 `controllers/` 下的默认布局 JSON，重排位置与尺寸 | 否（数据） |
| 样式 | 自写 `ControlButtonStyle` 配置（圆角、透明度、描边） | 否（数据） |
| 事件 | 用 4 个事件槽 + swipable 组合出多动作 | 否（数据） |
| 图标 | 本地 drawable，不走网络 | 否（资源） |

一句话：**差异全部落在数据与资源层，Java/Kotlin 一行不动。**

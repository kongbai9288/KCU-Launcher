## 4. 编译失败事故（本轮最重要）

第一次上传后 run **39819890952 失败**。

### 4.1 根因

`MainUI.refreshSkin()` 不是死代码——`AccountListItem.kt:199` 在调用它：

```kotlin
fun refreshSkinBinding() {
    image.unbind()
    texture.unbind()
    image.bind(...)
    MainActivity.getInstance().refreshAvatar(account)
    UIManager.instance.mainUI.refreshSkin(account)   // ← 跨界调用
}
```

`AccountListAdapter` 通过 `item.refreshSkinBinding()` 触发，`OfflineAccountSkinDialog` / `MicrosoftAccountSkinDialog` 也会调。

**删除 `refreshSkin` 后 unresolved reference，编译失败。**

### 4.2 为什么会漏

**我在本地 `raw/` 目录里 grep，那个目录只有我下载过的十几个文件，不是全仓。** 本地 grep 为 0 是假象。

正确做法是用 GitHub code search API 做全仓检索。检索结果显示 `refreshSkin` 命中 5 个文件（含 4 个 account UI），一眼可见。

### 4.3 连带发现两个 CI 缺陷

取证时发现**失败时根本拿不到日志**：

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | `BUILD_LOG` 写入在 `exit 1` **之后** | 失败时 GITHUB_ENV 不会被保留，上报永远拿不到日志尾部 |
| 2 | 上报步骤 `if` 依赖 `env.GRADLE_OK` | 该值由**失败步骤**写入，在后续 step 级 `if` 中不可靠 → 上报步骤 skipped |

修复：

```yaml
# 先写日志，再判失败
{ echo "BUILD_LOG<<EOF_DELIM"; tail -c 6000 /tmp/build.log; echo "EOF_DELIM"; } >> "$GITHUB_ENV"
if [ "$GE" -ne 0 ]; then echo "::error::..."; exit 1; fi

# 上报改用步骤 outcome，不依赖 env
if: ${{ always() && (steps.gradle.outcome == 'failure' || steps.gradle_debug.outcome == 'failure') && (arch 匹配) }}
```

修复后 run 39820845511 的上报步骤确实 success（此前 skipped），但仍未创建 issue（疑似仓库层限制 Actions 建 issue）。日志最终靠**全仓搜索定位调用点**解决，而非靠日志。

也就是说——**"皮肤预览 + 角色切换放一起"这个组合，在账号皮肤对话框里已经天然存在**，不需要新造容器。用户计划的落点可以直接选这里，而不是另建界面。

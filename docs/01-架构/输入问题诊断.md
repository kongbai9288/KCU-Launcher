# 触摸输入问题诊断

> 结论先行：**你说的三个毛病都是真的，而且我定位到了具体代码位置。但"换成别人的代码"解决不了根因——因为全行业都没解决。**
> 依据：本仓库已落地的 FCL 源码逐行阅读 + Android 官方文档 + 对 5 个启动器仓库的代码检索。

---

## 1. 三个问题的根因

### 1.1 滑动过程检测不到 —— 历史点批处理未处理

**位置**：`FCL/src/main/java/com/kongbai/kculauncher/control/view/TouchPad.java`、`ControlButton.java`

`ACTION_MOVE` 分支只取最新坐标：

```java
float newDownX = event.getX(pointerIndex);
float newDownY = event.getY(pointerIndex);
float frameDX = newDownX - downX;
float frameDY = newDownY - downY;
downX = newDownX;   // 锚点推进
downY = newDownY;
```

**没有遍历 `event.getHistorySize()`。**

Android 官方文档原文：

> The platform provides motion events to applications **in batches**, so a single event may contain a current position and multiple so-called historical movements. Applications should use `getHistorySize()` to get the number of historical samples, then retrieve and process all historical samples in order.

即：一次 `ACTION_MOVE` 回调里可能打包了 5～10 个采样点。只取 `getX()` 意味着**中间整段轨迹被丢弃**，只剩首尾差值。

实际表现：

| 现象 | 原因 |
|---|---|
| 快速滑动时视角不跟手 | 中间点丢失，只下发首尾差值 |
| 慢速精细移动反而抖 | 单帧差值噪声被灵敏度放大 |
| "过程检测不到" | Java 侧确实只看到了批次末点 |

### 1.2 点击难受 —— 单击判定阈值过严

**位置**：`TouchPad.java` 两处（`ACTION_UP` 分支）

```java
if (System.currentTimeMillis() - downTime <= 100
        && Math.abs(event.getX() - downX) <= 10
        && Math.abs(event.getY() - downY) <= 10) {
    // 才判定为点击
}
```

- **100ms**：手指从按下到抬起的正常时长常在 100～200ms，阈值过严
- **10px**：手指轻微滑动就超

结果：用户以为点了，实际没触发；或触发成了右键（BUILD 模式）而非左键。

`ControlButton` 也有同样的 100ms / 10px 判定。

### 1.3 点不到位置 —— 鼠标移动模式选错

**位置**：`control/MouseMoveMode.java`

```java
public enum MouseMoveMode {
    CLICK(0),
    SLIDE(1);
}
```

两种语义完全不同：

| 模式 | 行为 | 手指位置 = 光标位置？ |
|---|---|---|
| `CLICK` | `setPointer(event.getX(), event.getY())` 直接绝对定位 | **是** |
| `SLIDE` | `initialX + (x - downX) * sensitivity` 相对位移 | **否** |

在 `SLIDE` 模式下，手指按下去的位置**不是**光标位置，光标在按下瞬间的原位，靠后续相对移动推动。所以"点哪都点不到"——你得先把光标拖过去。

**这个是设置问题，不是代码问题。零改码即可解决。**

## 2. 换别人的代码能解决吗（实测对比）

对 5 个仓库检索 `getHistorySize`（历史点处理）的使用：

| 项目 | 命中数 | 命中位置 |
|---|---|---|
| FoldCraftLauncher（现基座） | 1 | `KCUInput.java`——**仅外接鼠标/指针捕获路径** |
| ZalithLauncher2 | **0** | — |
| PojavLauncher | **0** | — |
| Amethyst | **0** | — |
| MojoLauncher | 1 | `AndroidPointerCapture.java`——**同样仅指针捕获路径** |

**所有项目的触摸板路径都没有处理历史点批处理。**

也就是说：

- 换成 ZL2 的输入层 → §1.1 的毛病**原样保留**
- 换成 Pojav / Amethyst → 同样保留
- ZL2 触摸控制虽然是 2025-09 新做的（官方称 "revolutionary touch control"），但它解决的是**交互形态**（直接操作物品栏、手势），不是**采样精度**

**结论：没有现成的更好实现可以直接替换来解决你抱怨的这几个具体问题。**

## 3. 三条路径

### 路径 A：零改码（先试这个）

| 操作 | 解决 |
|---|---|
| 设置里把鼠标移动模式切到 **CLICK** | §1.3 点不到位置 |
| 调低鼠标灵敏度 | §1.1 抖动感 |
| 关闭"禁用手势" / 调手势模式 | §1.2 误判右键 |

**改动量：0。风险：0。建议先做。**

### 路径 B：最小补丁（改上游，但改动可控）

在 `TouchPad.java` / `ControlButton.java` 的 `ACTION_MOVE` 里补历史点遍历：

```java
// 先处理所有历史点，再处理当前点
for (int h = 0; h < event.getHistorySize(); h++) {
    float hx = event.getHistoricalX(h);
    float hy = event.getHistoricalY(h);
    处理增量(hx - downX, hy - downY);
    downX = hx; downY = hy;
}
处理增量(event.getX() - downX, event.getY() - downY);
```

同时放宽点击阈值：100ms → 250ms，10px → 16px。

**改动量：约 30～50 行，局限在两个文件。风险：低（纯 Java 侧，不碰 native 桥）。**

代价：这属于"改上游代码"，与你此前"把上游当 API、不改代码"的约束冲突，需要你明确授权。

### 路径 C：整体替换输入层

换成 ZL2 / Amethyst 的输入模块。

**风险：高。**

- 输入最终要过 `CallbackBridge` → `libpojavexec` 的 `input_bridge_v3.c`（native）
- 换 Java 层意味着要重新对齐 native 侧期望的事件协议
- ZL2 ahead 732 / behind 612，代码基线差异大
- **且如 §2 所述，它并没有解决 §1.1 的根因**

**结论：不建议。投入大、风险高、核心问题还在。**

---

## 4. 推荐

1. **先按路径 A 调设置**，尤其是切 `CLICK` 模式 —— 可能直接解决"点不到位置"
2. 若 §1.1 的跟手问题仍不能接受，走**路径 B**，我写一个最小补丁
3. **不走路径 C**

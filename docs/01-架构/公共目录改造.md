## 1. 被否决的 v0.13.0 实现

```java
if (legacy.exists() && !kcu.exists()) return legacy;
return kcu;
```

表面看能做到"要么全 FCL、要么全 KCU"。**但它的决策依据是"目录是否存在"，而存在性是可变的、可被外部改变的。** 这是根本缺陷。

## 2. 严格预估：会导致什么错误

### 错误 A：根路径漂移，存量数据"消失"（严重）

| 步骤 | 事件 |
|---|---|
| 1 | 迁移用户（`/sdcard/FCL/.minecraft` 有数据）安装 KCU，首启走 legacy |
| 2 | **任何外部行为创建了 `/sdcard/KCU`** |
| 3 | 重启：`kcu.exists()` 变 true → 条件失效 → 切到 KCU |
| 4 | 用户视角：游戏存档、版本、Mod **全部不见了** |

**这不是理论风险，是必然会发生的**：本项目的 KCU Migrator 天然会创建 `/sdcard/KCU`。我自己的工具就会触发这个 bug。

### 错误 B：误判后不可逆（严重）

一旦切到 KCU 分支，`loadPaths` 的 `init()` 会 `mkdirs` 出 `log` / `control` / `share` / `.minecraft`，**坐实** `/sdcard/KCU` 存在。此后 `kcu.exists()` 恒为 true，条件 `legacy.exists() && !kcu.exists()` 永远不成立——**再也回不到 FCL**。

首次误判 = 永久误判。

### 错误 C：无权限时 `exists()` 静默返回 false（较严重）

`targetSdk = 34`，Android 11+ 分区存储下，未授予 `MANAGE_EXTERNAL_STORAGE` 时应用无法 stat `/sdcard` 下非专属目录，`File.exists()` 返回 **false** 而非抛异常。

证据：`Config.java:149` 在**字段初始化期**就引用 `KCUPath.SHARED_COMMON_DIR`，意味着 `KCUPath` 类的静态初始化**早于** `loadPaths(context)`，即决策发生在拿不到 Context、权限很可能尚未授予的时刻。

场景：

1. 首次启动未授权 → `legacy.exists()`=false → 走 KCU
2. `init()` 尝试 `mkdirs /sdcard/KCU/.minecraft` → **若部分成功**（建出 KCU 但没建出 .minecraft）
3. 用户授权后重启 → `legacy.exists()`=true、`kcu.exists()`=true → 走 KCU
4. **用户的 FCL 数据被永久无视**

### 错误 D：多进程各自独立决策（中）

Manifest 声明了 `:crash` 与 `:jvm` 两个独立进程。每个进程独立加载 `KCUPath`、独立算一次。
若某进程启动时目录/权限状态恰好不同（例如 `:jvm` 在授权前启动），两个进程可能拿到**不同的根**，游戏去找错目录。

## 3. 对今后使用逻辑的干扰

| # | 干扰点 | 说明 |
|---|---|---|
| 1 | **迁移工具无法对齐** | Migrator 从外部看文件系统，它不知道启动器当时选了哪个根。它写 `/sdcard/KCU` 而启动器读 `/sdcard/FCL` → 数据对不上 |
| 2 | **manifest 契约无处安放** | 计划中的 `/sdcard/KCU/manifest.json` 依赖根路径。根会漂移，契约就失效 |
| 3 | **自定义 .so 双层目录失去依托** | `natives/<abi>/` 也在根下，同样受影响 |
| 4 | **无法向用户解释** | "你的数据没丢，在另一个目录"——但启动器自己都说不清是哪个 |

根路径是**整个公共目录体系的地基**。地基会漂移，上面所有设计都不可靠。

## 4. 修复：决策一次性并固化

```java
if (new File(kcu, KCU_ROOT_MARKER).exists())    return kcu;     // 已固化
if (new File(legacy, KCU_ROOT_MARKER).exists()) return legacy;  // 已固化
boolean legacyHasData = new File(legacy, ".minecraft").exists(); // 首次判定
File chosen = legacyHasData ? legacy : kcu;
try { marker.createNewFile(); } catch (Exception ignored) { }    // 固化
return chosen;
```

要点：

- **标记文件 `.kcu_root` 固化决策**，之后不再看目录存在性，外部创建目录也无法改变
- 判定"FCL 有数据"看 **`.minecraft`** 而非 `FCL` 本身——`log`/`control` 等目录可能单独残留形成空壳
- marker 写入失败（无权限）**不阻断**，下次启动重新判定——这正好修复错误 C

### 场景复核

| 场景 | 结果 |
|---|---|
| 全新用户（已授权） | 无 marker，`FCL/.minecraft` 不存在 → KCU，marker 写入成功 → 固化 ✅ |
| 迁移用户（已授权首启） | `FCL/.minecraft` 存在 → legacy，marker 写入 → 固化 ✅ |
| 迁移用户（**未授权首启**） | 无权限→判 false→KCU，marker 写入失败；授权后重启：仍无 marker，此时 `FCL/.minecraft` 可见 → legacy，marker 成功 ✅ **错误 C 已修** |
| 已固化后外部创建另一目录 | 有 marker → 不漂移 ✅ **错误 A、B 已修** |
| 用户手动删除根（含 marker） | 重新判定，等同重置，可接受 |

## 5. 仍未消除的风险（如实标注）

| # | 残余风险 | 状态 |
|---|---|---|
| 1 | 静态初始化期做磁盘 IO（写 marker） | 已 try-catch，一次性。**NOT PROVEN**，未真机验证是否触发 StrictMode |
| 2 | 多进程独立计算（错误 D） | **未修**。marker 固化后各进程结果趋同，但无跨进程同步保障。`:jvm` 进程行为待实机确认 |
| 3 | 两个根都无 marker 且都"有数据" | 优先 KCU。理论上不该出现 |
| 4 | marker 被迁移工具误删 | 会触发重新判定。需在 Migrator 侧约定不删隐藏文件 |

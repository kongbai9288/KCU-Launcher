## 0. 总原则：先看归属，再谈实现

这份规范的七节内容，**不属于同一个实现层**。必须先分流，否则会在错误的层级上做无用功。

| 节 | 内容 | 归属 | 本项目该做什么 |
|---|---|---|---|
| 一 | 意图分流、轨迹线性度、滚轮离散化 | **游戏内**（TouchController） | 不实现 |
| 二 | 点击判定、硬件否决、长按容错 | **游戏内**（TouchController） | 不实现 |
| 三 | Raw Input、首帧跳变、加速模型 | **游戏内**（TouchController） | 不实现 |
| 四 | 多指协同、模式隔离 | **游戏内**（TouchController） | 不实现 |
| 五 | 竞态防御、渲染帧同步 | **游戏内**（TouchController） | 不实现 |
| 六 | 异常兜底 | **游戏内** + 启动器侧少量 | 见 §4 |
| 七 | dp 阈值、底层鼠标伪装 | **启动器** | **本项目该做** |

理由沿用 v0.7.0 已论证的结论：TouchController 官方明确要求禁用启动器自带触摸手势，否则两套语义叠在同一条链路上会产生"预料之外的鼠标输入"。启动器重做一遍手势，既治不了 MC 的病，又会跟游戏内接管打架。

**但第七节是例外**——它讲的是"识别这个事件是手指还是鼠标"，属于**事件源判定**，发生在手势语义产生之前，天然在启动器侧。

## 2. 【修正】`mouseMoveMode` 默认就是 CLICK

v0.6.0 我判断用户"点不到位置"可能是处于 `SLIDE` 模式，建议切 `CLICK`。

**这个建议的前提是错的。**

实测 `MenuSetting.kt:195`：

```kotlin
var mouseMoveMode: MouseMoveMode = MouseMoveMode.CLICK
```

**默认就是 CLICK。** 用户并没有处于 SLIDE 模式，切换不能解决问题。

真正的根因见下一条。

## 3. 【新发现】点击阈值写的是 px，不是 dp

规范第七节第 1 条——「所有距离阈值必须使用 dp，绝不能写死 px」。

**上游确实违反了这个规则，而且是用户抱怨的直接成因。**

实测 `TouchPad.java`：

```java
// 第 247-248 行（捕获态）
&& Math.abs(event.getX() - downX) <= 10
&& Math.abs(event.getY() - downY) <= 10

// 第 330-331 行（非捕获态）
&& Math.abs(event.getX() - downX) <= 10
&& Math.abs(event.getY() - downY) <= 10
```

`getX()` 返回的是 **px**。这个 `10` 是 10 px。

| 屏幕密度 | 10 px 折算 |
|---|---|
| mdpi (1.0) | 10 dp |
| xhdpi (2.0) | 5 dp |
| xxhdpi (3.0) | 3.3 dp |
| xxxhdpi (3.5，常见于 2K 屏) | **2.9 dp** |

**在主流 2K 屏上，点击容差只有不到 3 dp** —— 手指任何微小位移都会超出，点击判定时常落空。

这与用户的原话完全吻合：

> 感觉点击非常难受，有时候压根就点不到位置

**这是真因，不是时间阈值。**

### 3.1 修还是不修

| 选项 | 判断 |
|---|---|
| 改手势逻辑让它变准 | ❌ 不做（层级错误，见 §0） |
| 仅把 `10` px 换成 `10` dp | ✅ **可做** |

理由：这是**纯单位修正，不是手势逻辑重写**。它不引入新的意图判定、不改变事件语义，只把已有的容差换算成与密度无关的单位。不违反"不在启动器层重做输入"的约束。

改法：`10` → `10 * density`（或 `ViewConfiguration.get(context).getScaledTouchSlop()` 这类系统标准值）。

状态：**待用户确认后再动**。因为改阈值会改变手感，需要真机对比，且当前主推路径是 TouchController。

## 4. 第七节第 2 条：底层鼠标伪装（新增模式）

> 用户原话：部分安卓机型的底层会把鼠标移动事件混在普通触摸里发上来，系统必须通过底层接口区分"这是玩家手指"还是"底层映射的鼠标"，防止自己处理自己的死循环。**这个是一个新的模式，放在启动以后的菜单中作为独立选项，这样方便观察与原来的区别。**

### 4.1 上游现状

上游**已有**部分能力，但形态不同：

| 已有 | 位置 |
|---|---|
| `event.isFromSource(InputDevice.SOURCE_MOUSE)` 分支，外接鼠标走独立路径并 `return true` 防穿透 | `TouchPad.java:188-198`、`260-265` |
| `handleExternalTouchButtons(event)`：指针捕获未生效时，外接鼠标点击以普通 touch 到达，补齐按键投递 | `FCLInput.java:700` |
| `handleExternalMouseEvent(event)`：处理 `ACTION_BUTTON_PRESS/RELEASE` + `ACTION_SCROLL` | `FCLInput.java:336` |
| `isPhysicalMouseMode`（默认 false）：实体鼠标模式下系统指针绝对坐标直接驱动光标 | `MenuSetting.kt:287`、`FCLInput.java:660` |

**差异**：上游的 `physicalMouseMode` 是「**外接**鼠标怎么驱动光标」，而用户要的是「**底层把鼠标伪装成触摸**时怎么识别并分开处理」。这是两件事：

| | 上游 `physicalMouseMode` | 用户要的新模式 |
|---|---|---|
| 场景 | 真的插了个鼠标/蓝牙鼠标 | 没插鼠标，但系统把某些事件伪装成触摸上报 |
| 识别依据 | `isFromSource(SOURCE_MOUSE)` | 需要在"看起来是触摸"的事件里分辨来源 |
| 当前 | 已实现 | **未实现** |

### 4.2 可用的识别手段（技术事实）

Android 提供三类判别依据：

| 手段 | 说明 |
|---|---|
| `event.getSource()` | 区分 `SOURCE_TOUCHSCREEN` / `SOURCE_MOUSE` / `SOURCE_STYLUS` / `SOURCE_TOUCHPAD` |
| `event.getToolType(i)` | 区分 `TOOL_TYPE_FINGER` / `TOOL_TYPE_MOUSE` / `TOOL_TYPE_STYLUS` / `TOOL_TYPE_ERASER` |
| `event.getButtonState()` | 非 0 时常指示鼠标按键状态 |

上游目前**只用 `getSource()`**，全仓库未见 `getToolType` 用于 FCL 输入路径（仅 `SDLSurface.java` / `SDLControllerManager.java` 有）。

**`getToolType` 是最可能的判别入口**：伪装场景下 `getSource()` 可能仍报 `SOURCE_TOUCHSCREEN`，但 `getToolType()` 会暴露 `TOOL_TYPE_MOUSE`。

⚠️ **这一点未在本项目源码或真机上验证**，属于技术推断。写入防错清单待办。

## 5. 规范全文归档

用户提供的 v5.0 规范原文七节，作为**验收测试依据**归档：

| 节 | 主题 | 核心约束力 |
|---|---|---|
| 一 | 意图分流 | 前 100ms 不发指令；动态观察窗 60~140ms；线性度 <1.15 判滑动、>1.3 判拖拽；<12dp 不算线性度；两阶段锁定；滚轮蓄水池 50ms/3 格 |
| 二 | 点击判定 | 位移 8~12dp + 正常抬起 = 点击；抬手瞬间接触面积未减小则**否决**；低端机无压力检测时忽略硬件、不阻塞点击；不要求"必须短于 50ms" |
| 三 | 视角手感 | Raw Input 默认不加滤镜；首帧跳变打折 30% 或从第二帧起算；转向加速非线性映射 |
| 四 | 多指协同 | GUI 模式单主控手指；Game 模式左右半屏分治；一个按键只归一根手指 |
| 五 | 竞态防御 | 等真实渲染帧而非底层回调；切换后 1~3 帧只更新坐标不触发点击；跨模式事件直接丢弃 |
| 六 | 异常兜底 | 系统拦截/下拉通知栏强制松开左键；切后台归零；非主控手指抬起不重置 |
| 七 | 设备兼容 | 阈值一律 dp；识别底层鼠标伪装 |

**这些条款的作用**：当实机验收时，逐条对照检查。其中一到六节的验收对象是 **TouchController（游戏内）**，不是启动器。

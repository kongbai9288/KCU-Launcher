## 1. API 终点追踪

```
SettingUI extends FCLMultiPageUI
  → getPageCount() / createPage(int) / getTabTitles()
      → 【终点】FCLMultiPageUI.setupPages(container, tabLayout)

FCLPage(context, id, @LayoutRes resId)
  → setContentView(resId) → LayoutInflater.inflate
  → onCreate()
      → 【终点】findViewById(contentView)
```

| 方法 | 位置 |
|---|---|
| `getPageCount()` | abstract，`FCLMultiPageUI` 抽象声明，子类实现 |
| `createPage(int)` | abstract |
| `getTabTitles()` | 可空，默认 null |

`FCLMultiPageUI` 内部第 277 行 `return getPageCount()` 用于 adapter。改数量只需改子类三处，无外部硬编码。

`getPageCount` 的实现共 5 处：VersionUI / ControllerUI / **SettingUI** / ManageUI / 基类声明。互不影响。

## 3. 严格自我审核

### 3.1 会导致什么错误

| # | 错误 | 处置 |
|---|---|---|
| 1 | **`clearMarks()` 内部已调 `KcuAgeGate.reset()`**，页面里再调一次是冗余 | **已移除**页面内重复调用及对应 import |
| 2 | 网络请求在主线程会 ANR / `NetworkOnMainThreadException` | **已防**：走 `Schedulers.defaultScheduler()` |
| 3 | 文件删除在 UI 线程卡顿 | **已防**：同上 |
| 4 | `Schedulers.defaultScheduler()` 是否真实存在 | **已核实**：`Schedulers.java:62` |
| 5 | 令牌为空发起请求 | **已防**：前置校验并提示 |
| 6 | 未校验就能点清除 | **已防**：按钮初始 `setEnabled(false)`，`doClear` 再判一次 `verified` |
| 7 | 校验成功后换页面再回来，`verified` 丢失 | 页面随 ViewPager 创建/销毁，**预期**会重置，需重新校验 |
| 8 | `getPageCount` 改了但 `getTabTitles` 长度不匹配 | **已同步**加一项，5 对 5 |
| 9 | `KcuUi.root()` 本身有 padding，再放进已有 padding 容器会过宽 | 布局 XML 内 LinearLayout 无 padding，仅 `KcuUi.root` 提供 |

### 3.2 对今后使用逻辑的干扰

| # | 干扰 | 状态 |
|---|---|---|
| 1 | 设置页从 4 个页签变 5 个，横屏可能挤 | 需实机确认页签栏宽度 |
| 2 | 开发者模式状态有缓存，`clearMarks` 后调 `refresh()` 已刷新 | 页面也调了 `refreshState()` |
| 3 | 清除标记会清掉年龄声明，下次启动重新弹年龄页 | **预期行为**，页面文案未提示，需补 |
| 4 | 页签「开发者」对所有用户可见 | 页内无敏感操作入口（未校验不能清除），可接受 |

### 3.3 模拟使用逻辑

| 路径 | 结果 |
|---|---|
| 打开设置 → 第 5 个页签 | 显示「开发者」✅ |
| 进页面，未放 dev_mode | 状态「未开启」，显示路径 ✅ |
| 放对文件后进页面 | 状态「已开启」✅ |
| 点重新检测 | 刷新状态 ✅ |
| 令牌为空点校验 | 提示，不发起请求 ✅ |

| 未校验点清除 | 禁用状态点不到；`doClear` 也有兜底判断 ✅ |
| 校验后点清除 | 后台执行，返回清除项数，状态刷新 ✅ |
| 无网络点校验 | 异常捕获返回 false，提示未通过 ✅ |
| 旋屏 / 切后台回来 | 页面重建，`verified` 归零，需重新校验 ✅ |
